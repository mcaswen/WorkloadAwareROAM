# 新功能 / 模块实现规划文档规范

本规范用于代码修改前的实现规划。

规划文档的目标是：

* 让人类在代码实现前 Review 关键架构决策。
* 让后续 Agent 明确知道应该如何实施。
* 提前确定模块边界、职责、文件结构、依赖关系和实施阶段。
* 避免 Agent 在实现过程中根据局部便利自行改变架构。

规划文档描述的是**目标状态（To-Be）**。
当前代码事实应引用对应的 Codebase Facts 文档，不应在规划中重复大量源码细节。

## 规划类型与粒度

开始编写规划前，必须先判断当前任务属于 **大规划（Major Plan）** 还是 **小规划（Minor Plan）**，并据此决定文档详细程度。

### 大规划（Major Plan）

适用于：

* 新增一个完整模块或子系统。
* 大规模重构已有模块。
* 引入新的架构层、核心抽象或主要数据流。
* 涉及较多文件、多个组件或多个实施阶段。
* 会明显改变模块边界、依赖方向、生命周期或公共接口。

大规划必须进行完整架构设计，并拆分为多个可独立实现和验证的阶段。

应重点明确：

* 整体目标、范围与非目标。
* 当前架构和可复用能力。
* 目标分层、模块边界和依赖方向。
* 目录、文件和核心类型规划。
* 数据流、控制流、生命周期和关键接口。
* 重要数据结构、算法与设计模式。
* 各阶段的实现内容、依赖关系和 Validation。
* 测试策略、主要风险、迁移方案和 Open Questions。
* 完成后的目标架构。

大规划的重点是让人类能够在实现开始前完整 Review 整个模块的架构方向。

### 小规划（Minor Plan）

适用于：

* 修复一个 Bug。
* 实现大规划中的一个阶段。
* 在已有模块中增加一个局部功能。
* 小范围修改现有行为。
* 影响文件数量较少，且不会重新定义整体架构。

小规划不需要机械填写完整的大规划模板，应保持简洁，只记录本次修改真正需要确定的内容。

通常至少应包含：

* 问题 / 目标。
* 修改范围和非目标。
* 相关当前实现与根因。
* 计划修改、创建、移动或删除的文件。
* 每个相关文件的职责以及为什么修改应发生在这里。
* 是否应 Reuse / Extend / Wrap / Create。
* 关键数据流、状态变化或调用关系（仅在相关时）。
* 实现步骤。
* 对应测试与 Validation。
* 风险或仍需确认的问题。

即使是小规划，也不能跳过**文件归属和职责边界判断**。

不得因为任务较小，就默认：

* 直接修改当前文件。
* 把新职责塞入已有类。
* 复制已有数据结构或算法。
* 通过增加特殊分支和 flag 进行补丁式实现。

小规划仍应检查是否存在更合理的复用、抽象、拆分或文件归属方式，只是不需要展开与本次修改无关的整体架构。

文件规范：大规范和小规范统一放置在 ../Docs/Plans/<对应模块名> 下

### 判断原则

规划粒度应与**架构影响范围**匹配，而不是单纯根据预计代码行数判断。

一个改动只有几十行，但如果改变公共接口、ownership 或依赖方向，仍可能属于大规划。

一个阶段可能修改多个文件，但如果整体架构已经在上层 Major Plan 中确认，则可以使用 Minor Plan，只描述当前阶段的具体实现。

原则是：

**大规划负责确定系统级架构；小规划负责在已知架构边界内安全完成局部变化。**


## 1. 前置分析

规划前必须：

* 阅读相关开发规范、已有规划和 Codebase Facts。
* 扫描与任务直接相关的现有实现。
* 确认已有组件、工具、数据结构和抽象。
* 理解当前模块边界和依赖方向。

对于新增能力，应先判断：

* **Reuse**：直接复用已有能力。
* **Extend**：扩展已有能力。
* **Wrap**：通过适配层使用已有能力。
* **Create**：确实需要创建新组件、模块或文件。

如果需求存在关键歧义、明显风险或与项目边界冲突，应先提出问题，不得直接选定一种解释进入实现。

---

## 2. 背景与目标

简要说明：

* 当前问题是什么。
* 为什么需要本次修改。
* 本阶段需要达到什么结果。
* 如何判断本阶段完成。

目标必须具体、可验证，避免使用“优化架构”“完善系统”等模糊表述。

---

## 3. 范围与非目标

明确：

### In Scope

本阶段会实现、修改或重构什么。

### Out of Scope

本阶段明确不处理什么。

非目标用于限制 Agent 自行扩大任务范围。

---

## 4. 当前架构摘要

只记录与本方案直接相关的当前事实：

* 当前主要入口。
* 当前核心组件。
* 当前职责分布。
* 当前依赖关系。
* 可直接复用的能力。
* 当前影响方案的重要限制。

详细信息引用 Codebase Facts，不重复完整描述。

---

## 5. 方案概述

用较高层级说明目标方案：

* 新能力属于哪个模块或层级。
* 由哪些主要组件组成。
* 每个组件承担什么职责。
* 如何接入现有系统。
* 哪些现有能力会被复用。

应尽量提供简洁的结构图，例如：

```text
Scheduler
   ↓
Cache
   ↓
Shared Data Structure

Scheduler
   ↓
Core Algorithm
```

这一部分应让人类能够快速判断总体设计方向是否合理。

---

## 6. 模块与职责设计

对于新增或发生明显变化的核心组件，说明：

* 组件名称。
* 所属层级或目录。
* 核心职责。
* 明确不负责什么。
* 主要上游和下游。
* 生命周期或 ownership（如果重要）。

鼓励清晰分层、高内聚和细粒度职责划分。

数据结构、核心算法、策略、调度/编排、缓存、状态管理和通用工具在职责独立时应合理分离。

对每项新增职责，明确选择：

* **Reuse**：复用已有抽象
* **Extend**：扩展已有抽象
* **Wrap**：包装已有能力
* **Create**：创建新的抽象、组件、模块或文件

---

## 7. 目录与文件规划

必须给出规划后的主要目录和文件结构，例如：

```text
FlowField/
├── Data/
│   └── FieldBuildKey.cs
├── Build/
│   └── FieldBuilder.cs
├── Cache/
│   └── FieldBuildCache.cs
└── Scheduling/
    └── FieldBuildScheduler.cs
```

对于每个重要文件记录：

* **Action**：Create / Modify / Move / Split / Delete
* **Responsibility**：文件负责什么
* **Reason**：为什么该职责属于这里
* **Key Contents**：主要类型或关键接口

不要提前写大量实现代码。

---

## 8. 依赖与接口

说明主要依赖方向，例如：

```text
Scheduling → Build
Scheduling → Cache
Cache → Shared

Build ×→ Scheduling
Shared ×→ Feature Module
```

对于新增或修改的重要接口，简要说明：

* 谁调用。
* 主要输入输出。
* 核心行为。
* ownership / 生命周期要求。
* 同步、异步或线程限制（如果重要）。

只规划架构级接口，不需要提前定义所有 helper 方法。

---

## 9. 数据流与关键执行流程

描述实现完成后的主要数据流和控制流。

例如：

```text
BuildRequest
→ Scheduler
→ Cache lookup

Hit:
→ Commit Result

Miss:
→ Builder
→ Build Result
→ Cache
→ Commit Result
```

只展开最重要的业务路径和关键分支。

对于 Job、异步、跨帧或 GPU 流程，应明确主要阶段和同步点。

---

## 10. 关键设计决策

记录真正影响架构的决策，例如：

* 为什么建立独立 Cache，而不是塞入 Scheduler。
* 为什么使用 Strategy。
* 为什么某数据属于 Shared。
* 为什么采用接口隔离具体实现。

如果存在明显替代方案，应简要记录：

* Option A
* Option B
* Selected
* Reason

只记录重要取舍，不需要为普通实现细节写决策记录。

---

## 11. 实施阶段

对于**大规划**，要将实现拆成可独立验证的阶段，每个小阶段在实施前需要单独的**小规划**。

例如：

### Phase 1 — Data & Core

* 新增数据结构和核心组件。
* 不接入现有运行路径。

**Validation**

* 编译通过。
* 核心测试通过。

**实现情况**

### Phase 2 — Integration

* 接入现有 Scheduler。
* 完成主要执行路径。

**Validation**

* 集成测试。
* 现有行为不回归。

**实现情况**

### Phase 3 — Cleanup & Review

* 删除旧路径。
* 补充验证。
* 执行架构审查。

**实现情况**

每个阶段应说明：

* 做什么。
* 依赖什么。
* 如何验证完成。

---

## 12. 测试与验证

测试与实现同等重要。每个 Implementation Phase 都必须包含对应的 Validation，不能把测试集中到最后统一处理。

测试应围绕核心问题设计，至少覆盖：

正常路径与关键边界条件。
合理输入、非法输入和必要的输入门禁。
核心状态变化与重要分支。
输出内容、数量、范围、关系或最终状态的正确性。
本次修改可能影响到的已有行为和回归风险。
对性能、并发、生命周期敏感的功能，增加对应专项验证。

不得仅以“编译通过”“没有异常”“返回非空”作为充分验证。

对于核心算法或系统，应尽量验证结果是否正确，而不仅是流程是否执行完成。

每个阶段应明确：

使用什么输入。
检查哪些输出或状态。
什么条件满足后才能认为该阶段完成。

如果测试暴露出规划中的错误假设、遗漏边界或新的架构问题，应先修正规划或设计，不要通过降低断言或打补丁绕过问题。

## 13. 风险与待确认事项

记录会影响实现或架构的重要风险。

例如：

```text
Risk:
BuildKey 可能无法完整描述 Build Result 的生成条件。

Impact:
可能产生错误缓存命中。

Mitigation:
实现 Cache 前确认所有影响 Build 的输入。
```

仍需要人类决定的问题统一列入：

### Open Questions

对于每项问题应给出：

* 问题。
* 可选方案。
* 推荐方案。
* 推荐理由。

**存在会影响核心架构的 Open Question 时，不得直接进入实现。**

---

## 14. 目标架构摘要

规划末尾用简短形式总结最终设计：

### Directory

主要目录和文件。

### Responsibilities

各核心组件分别负责什么。

### Dependencies

主要依赖方向。

### Core Flow

最重要的数据 / 控制流。

这一部分用于人类最终快速 Review。

---

## 15. 实现偏离规则

实现过程中如果发现必须改变：

* 目录结构。
* 核心文件职责。
* 模块边界。
* 公共接口。
* 依赖方向。
* 关键抽象或设计模式。

不得静默偏离规划。

应先：

1. 说明发现的新事实。
2. 说明原规划为什么需要调整。
3. 提出修改方案及影响。
4. 更新规划。
5. 获得确认后继续实现。

普通局部实现细节不需要重新审批。

---

# 规划完成标准

规划应能够让人类快速回答：

* 为什么要做？
* 做什么、不做什么？
* 新能力放在哪里？
* 为什么放在那里？
* 有哪些模块、文件和核心类型？
* 各自负责什么？
* 谁依赖谁？
* 数据和控制如何流动？
* 实现分几个阶段？
* 如何验证？
* 有哪些风险或尚未确认的问题？

如果这些问题仍无法回答，应继续完善规划。
