## 时序说明了什么

test129 首轮接收派发 12.762ms，四个任务墙钟之和 26.582ms，最长任务 12.626ms，主线程等待 12.670ms；最后任务到派发返回约 0.043ms。主要时间在实际认证工作和分块不均衡，不能把整个 wait 都算成线程池浪费。

| 场景 / 阶段 | 派发平均 ms | 平均 Σ任务墙钟 / (任务数 × 最长任务) | 实际线程数量 |
| --- | ---: | ---: | --- |
| test129 接收 | 5.630 | 0.619 | 4 |
| test129 回收 | 5.081 | 0.735 | 4 |
| test129 面填写 | 0.078 | 0.355 | 1 |
| test129 网格填写 | 0.075 | 0.463 | 1～2 |
| Peking 投影 | 5.251 | 0.964 | 4 |
| Peking 评分归约 | 5.663 | 0.638 | 4 |
| Peking 接收 | 1.573 | 0.802 | 4 |
| Peking 面 / 网格填写 | 0.065 / 0.064 | 0.334 / 0.313 | 1 |

该比例只是任务区间长度分布，不是 CPU 利用率、理论 span 或调度最优性。四份很短任务由一个线程领取完成是实际记录，不能据任务数量宣称四核并行；也不构成本轮改变调度或任务粒度的授权理由。

Peking 五次视图变化中，`BuildOrders` 共 65.364ms，`PublishView` 共 40.527ms，加上投影与评分派发，明显区别于约毫秒级静止更新。结合 perf 的 `IsBoundary` 自身 13.44%，建序需要同时核查资格查询与有序结构，不只优化 tree insertion。

## 函数调用数量与区间

| 区间 | test129 次数 / 含调用 ms | Peking 次数 / 含调用 ms |
| --- | ---: | ---: |
| `gtp.receivers` | 512 / 14.443 | 512 / 9.779 |
| `gtp.fit` | 2693 / 89.001 | 3103 / 25.135 |
| `gtp.measure` | 614 / 122.749 | 64 / 5.106 |
| `gtp.donor` | 512 / 116.100 | 64 / 6.115 |
| `gtp.accepts` | 8268 / 0.317 | 64 / 0.066 |
| `gtp.reservation` | 8 / 12.697 | 8 / 0.357 |
| `gtp.samples.prepare` | 8 / 22.001 | 4 / 1.064 |

`Donor/Fit/Measure` 存在父子关系，上表不可相加。Tracy self 只扣已标记的同线程子区间；`Measure` 没有给每 Q 的 ErrorBounds 发事件，所以其 self 仍包括完整数值下层工作。perf 恰好补上这部分：test129 的区间数值与精确算术是真实 CPU 热点。

`Accepts` 次数多但区间总成本小，不能把“减少重复 acceptance 调用”直接当作数量级提速来源。完整 pair/reservation 包含其他数据结构工作，需与这一便宜比较函数分开。这是 profiler 对原猜测优先级的实质修正。
