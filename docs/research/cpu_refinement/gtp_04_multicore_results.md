# GTP-04：有限多核与家族上下文结果

2026-09-14；[小规划](../../plans/cpu_refinement/gtp_04_multicore_plan.md)。**同任务多核执行成立，原型四阶段闭环；当前结果不支持直接作为 Legacy 的性能替代品。** 最终同会话环境复核见 §7：完整收益约 1.94×/1.47×，初次单线程回归没有稳定复现；持续质量风险保留

§2～5 保留最初两组数据及当时的定位过程，不覆盖或选择性删除。当前性能判断及接入估算以 §7 的预登记同会话核查为依据；仍只是有限进程探索，不是正式统计重复

## 1. 输入、环境和验证

Ubuntu / WSL2，AMD Ryzen 9 9950X3D，16 核 32 逻辑处理器；GCC 15.2 Release，核心关闭 fast-math 和浮点收缩。B 单线程，C 固定 4 线程，正常 v1 / LocalCenterRefit / no-height-guard。两场景仍从 sample14 初始化，八次视图为 14,14,14,15,16,17,18,14

每场景 B/C 各一个诊断进程、一个计时进程，无暖机和统计重复。发现单线程较 GTP-03 变慢后，仅增加一组同期旧/新二进制定向复测。全部原始结果保留在 Git 忽略的 `benchmark-output/cpu-refinement/gtp-04/`：`diagnostic-01`、`timing-01`、`regression-check-01`、`family-01`、`provenance.json`、`verification.json` 和旧二进制

B/C 所有 16 个对应更新的需求、尝试、事务、逻辑工作计数、质量及最终几何逐值一致；每种模式计时/诊断网格也一致。全量状态、样本、有序索引、输出和 Pending 由诊断 oracle 核查。旧/新 B 同期复测的工作量及几何相同，没有因并行改写选择规则

解析检查覆盖真实四线程 rendezvous、私有计数归并、任务异常排空、缺失 Dispatch 拒绝、持续串并行结果、视图评分和准备失败后旧代际/Pending 保持。最终仅修正探针对已存在输出目录的失败记录归属，算法核心未再修改；定向验证拒绝覆盖，不重跑自然矩阵。测量及最终入口二进制哈希分别记录

代码结构变化为私有分块账本、提案结果延后有序收集、donor 提前认证及函数边界变化；逻辑计数完全相同，没有新增样本、重放或全域扫描。剩余每操作成本变化可能涉及布局/编译/缓存及运行环境，当前没有硬件证据定位到单一原因，标记 **未解决**，不编造根因。Peking 的整段 +2.68% 不触发追加追究

本阶段仅把该实现保留为隔离实验候选，不能据此替换 GTP-03 单线程参考或宣称生产性能无损。生产路径未修改。依已授权有限 Gate 收口，不自动启动布局/分配器大优化；后续接入前需单独处理此项

## 5. Classic/DOD 家族上下文

各家族从自身初态重放 0～13，随后执行同样八个视图。相同地形尺度、预算、阈值、相机；恢复正常默认执行策略，关闭三类诊断开关。Classic 实际 1 线程，DOD 实际 8 线程。没有复制状态执行 Legacy，也没有将新原型目标传给旧算法

| 场景 | Classic 八次 build | DOD 八次 build | 新 C 八次 update |
| --- | ---: | ---: | ---: |
| test129 | 4.515 | 4.829 | 166.859 |

这是不同算法、初始历史和接受条件的现实量级上下文，不能作为同任务线程倍率。尤其不能只看新 C 对 B 的加速，忽略其绝对时间仍高于已有实现

## 7. 最终同会话环境核查

在最终进程核查中发现 WSL 重新启动（systemd/udev 等进程仅运行约 1～3 秒），早期工具调用的短测可能混入启动后台负载。因此先补登记协议，再且仅再运行 `session-stable-01`：保持同一个 WSL 会话存活，等待启动 40 秒，采两秒 /proc/stat；当时空闲比例 99.984%。随后固定 test 旧 B→C→新 B、Peking 新 B→旧 B→C，各配置一个进程；每家族/场景再一个进程，无暖机、诊断重跑或样本扩展

CPU 空闲快照只排除明显启动干扰，不等于锁频、固定核亲和或整段无外部干扰。它提供更明确的运行边界，不能制造正式置信区间
