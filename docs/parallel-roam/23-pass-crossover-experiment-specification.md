# Workload-Aware ROAM：Pass 与 Crossover 实验说明

本文档规定项目中各个 pass 的职责、合法策略、可能出现 crossover 的原因以及第一轮正式实验规模。
实验首先回答两个问题：

1. 每个 pass 的合法实现是否会随工作量变化而发生稳定的性能胜负反转
2. 如果存在反转，能否用执行前已经知道或能够低成本取得的特征解释反转位置

只有先得到这两类证据，后续离线参考和在线选择策略才有明确的研究对象。

## 1. 项目中的 Pass

当前一次 DOD 更新按下面的逻辑顺序执行：

```text
准备
  -> 合并评分
  -> 合并拓扑
  -> 细分评分
  -> 细分拓扑
  -> 网格提交
  -> 收尾
  -> CPU 上传
```

项目把其中六项作为独立实验 pass。准备和收尾没有可切换策略，只进入整帧成本。

| Pass | 目的 | 主要输入 | 主要输出 | 当前合法策略 |
| --- | --- | --- | --- | --- |
| 合并评分 | 刷新 `Q_m` 中全部现有条目的屏幕误差并重新建堆 | 当前合并队列、相机和投影参数 | 更新后的优先级堆 | `SerialRefresh`、`ParallelRefresh` |
| 细分评分 | 刷新 `Q_s` 中全部现有条目的屏幕误差并重新建堆 | 当前细分队列、相机和投影参数 | 更新后的优先级堆 | `SerialRefresh`、`ParallelRefresh` |
| 合并拓扑 | 校验菱形、提交合并、维护活动集合和长期队列并收敛 | 冻结合并候选、预算和当前拓扑 | 合并后的持久拓扑与编辑记录 | `SerialImmediate`、`ParallelAssisted` |
| 细分拓扑 | 提交细分、处理强制闭合和预算并维护长期队列 | 冻结细分候选、预算和当前拓扑 | 细分后的持久拓扑与编辑记录 | `SerialImmediate`、`ParallelAssisted` |
| 网格提交 | 把拓扑编辑映射到长期网格槽位并生成脏区间 | 拓扑编辑、槽位所有者和活动叶 | CPU 网格与更新区间 | `SerialDirty`、`ParallelDirty`、`SerialFull` |
| CPU 上传 | 把相同 CPU 网格数据交给图形缓冲区 | CPU 网格、脏区间和缓冲区容量 | 可绘制的图形缓冲区 | `DirtyRange`、`FullBuffer` |

### 1.1 每个 Pass 的真实串行、并行、增量和全量语义

| Pass | 串行/并行语义 | 增量/全量语义 |
| --- | --- | --- |
| 合并评分 | 评分循环可以串行或并行，建堆仍在主线程完成 | 队列成员局部维护，但每次刷新全部现有优先级 |
| 细分评分 | 评分循环可以串行或并行，建堆仍在主线程完成 | 队列成员局部维护，但每次刷新全部现有优先级 |
| 合并拓扑 | 串行立即提交，或并行辅助提交安全内部候选后串行收敛 | 对持久拓扑执行增量事务，不存在全量拓扑策略 |
| 细分拓扑 | 串行立即提交，或并行辅助提交安全内部候选后串行处理闭合与预算 | 对持久拓扑执行增量事务，不存在全量拓扑策略 |
| 网格提交 | 脏槽位可以串行或并行写入；完整网格当前只有串行写入 | 支持增量脏槽位和串行全量写入 |
| CPU 上传 | 图形接口调用都由渲染线程提交，不宣称并行上传 | 支持脏区间和完整缓冲区上传 |

`Automatic` 只是策略选择入口，不是新的实验策略。实验必须同时记录请求策略、实际策略和回退原因。发生无工作、工作量不足、首次网格建立、缓冲区扩容或 D3D12 帧槽积压时，实际策略可能与请求策略不同。

### 1.2 不单独建立 Crossover 的统计项

下面这些项目仍需计时或记录，但当前不是独立策略 pass：

- 准备：处理输入变化、缓存和必要的拓扑重置
- 收尾：整理统计并发布渲染数据
- 预算叶收集和最终叶收集：当前直接使用持久活动视图，没有独立实现可比较
- 独立误差计算：屏幕误差已经包含在两类评分 pass 中
- 候选快照、分块建立、结果整理、索引与队列刷新：属于对应拓扑 pass 的内部成本
- 队列成员维护：由拓扑事务立即增量完成，不是独立的评分策略
- `FrontierMaintenance`：只保留为主实验完成后的可选研究，不进入当前策略集合

## 2. 各 Pass 为什么可能出现 Crossover

Crossover 指同一 pass 的两个合法策略在不同工作量区域中互换胜负。只有结果等价且比较包含完整 pass 成本时，才能把性能反转称为 crossover。

### 2.1 合并评分

串行刷新在 `Q_m` 很小时通常更有优势，因为线程唤醒、任务切分和结果同步可能比评分计算本身更贵。队列增大后，并行评分可以分摊每个条目的屏幕误差计算，因而可能超过串行实现。

反转位置主要受以下因素影响：

- `Q_m` 条目数量
- 实际线程数量
- 单条评分计算成本
- 串行建堆占完整 pass 的比例
- 线程任务是否均匀

建堆始终是串行部分，因此队列继续增大时，并行收益也可能提前进入平台期。

### 2.2 细分评分

基本机制与合并评分相同，但 `Q_s` 通常更大，并且会受到当前活动叶规模和相机变化影响。预期小队列由串行刷新占优，大队列更可能由并行刷新占优。

合并评分和细分评分必须分别报告。Classic 在统一优化前刷新两条队列，DOD 会在合并后刷新细分队列，因此两类评分的工作量分布不能合并成一个“评分总量”。

### 2.3 合并拓扑

并行辅助合并只有在存在足够多、彼此独立并且能均匀分配到多个分块的安全菱形时才可能获益。候选很少、边界比例高或大量候选在前一批提交后失效时，候选快照、分块、结果整理和串行收敛会使串行实现更快。

主要影响因素是：

- 合并候选数量
- 安全内部候选比例
- 边界候选比例
- 非空分块数量与负载不均衡
- 提前提交成功数量
- 队列失效、索引刷新和串行收敛成本

当前固定视点回归已经观察到合并阶段实际使用最多 8 个线程提前提交，因此该 pass 已具备形成 crossover 的基本条件，但仍需正式矩阵确认反转位置。

### 2.4 细分拓扑

细分比合并更容易受到依赖链限制。候选需要强制细分邻居、跨越分块边界、缺少可复用子节点或接近预算上限时，都会退回串行尾部。即使候选总量很大，也不代表可并行提交的工作足够多。

主要影响因素是：

- 细分候选数量
- 安全内部候选比例
- 边界候选比例
- 强制闭合需求
- 剩余三角形预算
- 非空分块数量与负载不均衡
- 并行提前提交数量和串行尾部比例

当前六点冻结状态回归中，细分候选都因安全条件不足进入串行尾部。因此这里首先要验证的是“是否存在有效并行区域”，然后才是反转位置。如果扩展工作量后仍没有真实并行提交，就不把细分拓扑保留为在线选择维度。

### 2.5 网格提交

网格提交可能形成三种策略的分段胜负：

```text
变化很少          中等或较多局部变化          接近全量变化或区间极度破碎
SerialDirty   ->  ParallelDirty          ->  SerialFull
```

这不是预设结论，而是需要验证的候选形状。实际反转主要由以下因素决定：

- 活动三角形数量
- 更新三角形数量和更新比例
- 脏区间数量
- 区间平均长度和碎片度
- 并行任务粒度
- 完整网格连续写入的带宽优势

`ParallelFull` 当前不存在，因此不能出现在实验表或策略标签中。

### 2.6 CPU 上传

脏区间上传减少传输字节数，但每个区间都需要图形接口调用。区间很少且总字节数较小时，`DirtyRange` 应当更有优势；脏数据比例很高或区间高度碎片化时，多次调用的固定成本可能超过一次完整上传，此时 `FullBuffer` 可能更快。

主要影响因素是：

- 上传字节数和完整缓冲区字节数
- 脏字节比例
- 上传区间数量和平均长度
- 缓冲区是否扩容
- D3D12 帧槽是否需要追赶多个更新版本

首次建立、扩容和帧槽积压造成的强制完整上传属于回退场景，不能作为 `DirtyRange` 主动选择失败的性能样本。

## 3. 核心实验规模

本节固定第一轮正式 pass crossover 实验的规模。后续只有在核心实验得到稳定结果后才扩展线程数量、硬件和地形，避免一开始形成不可执行的全组合。

### 3.1 固定环境

| 项目 | 核心设置 |
| --- | --- |
| 构建 | `RelWithDebInfo`，记录 Git commit 和编译器版本 |
| CPU | 一台参考 CPU，固定电源策略和后台负载 |
| 线程 | 串行策略固定 1 个线程；并行策略上限固定 8 个线程 |
| CPU pass | 以无窗口重放为主，不包含渲染和垂直同步 |
| 上传 pass | OpenGL 为主实验后端，关闭垂直同步 |
| D3D12 | 只做规定规模的交叉检查，不展开完整主矩阵 |
| 分辨率 | 1280×720 |
| 视场角 | 60° |
| 近远裁剪面 | 0.1 / 500 |
| 计时 | 每个策略记录完整 pass 墙钟时间，内部子阶段只用于解释 |

### 3.2 地形和预算

核心实验固定两个地形，每个地形使用三个预算等级：

| 地形 | 地形尺寸 | 高度缩放 | 最大深度 | 细分/合并阈值 | 预算等级 |
| --- | ---: | ---: | ---: | ---: | --- |
| `Hm_Terrain_Test_129.pgm` | 30 | 4 | 14 | 4 px / 2 px | 512、4096、20000 |
| `Hm_Terrain_Peking_513.png`（实际 547×547） | 80 | 12 | 20 | 0.25 px / 0.1 px | 20000、80000、200000 |

两个地形使用不同阈值，是为了让受控小高度图和较大高度图都覆盖低工作量、持续修改和预算压力区域。每个地形内部的策略比较必须使用完全相同的阈值，不能为某个策略单独调参。

第二个文件的历史名称包含 513，但 PNG 的 IHDR 和当前加载结果都是 547×547。正式报告使用实际尺寸，不从文件名推断输入规模。项目没有保存该文件的测绘来源说明，因此不把它描述为经过地理标定的真实 DEM。

### 3.3 三条固定轨迹

每条轨迹固定为 64 个离散采样点。地形中心为原点，Y 轴向上，`R` 表示地形尺寸，采样编号为 `k=0..63`：

| 轨迹 | 采样方式 | 主要覆盖的工作量 |
| --- | --- | --- |
| A：稳定慢移 | `θ=-5°+10°k/63`，相机为 `(0.85R sinθ, 0.30R, 0.85R cosθ)`，始终看向 `(0, 0.05R, 0)` | 小规模评分、少量拓扑变化、稀疏网格更新 |
| B：接近后远离 | `k=0..31` 令 `q=k/31`，距离为 `(1.60-1.35q)R`、高度为 `(0.55-0.35q)R`；`k=32..63` 令 `q=(k-31)/32`，距离为 `(0.25+1.35q)R`、高度为 `(0.20+0.35q)R`，相机为 `(0,hR,dR)` 并始终看向 `(0,0.05R,0)` | 连续细分、连续合并以及中高更新比例 |
| C：快速转向与预算重入 | 相机固定在 `(0, 0.30R, 0.95R)`；每 8 点依次看向 `(-0.30R,0.05R,0)`、`(0.30R,0.05R,0)`、`(0,0.05R,-0.30R)`、`(0,0.05R,0.30R)`，循环两次 | 突发候选、预算满载重分配、边界比例和负载不均衡 |

轨迹坐标、朝向和采样编号必须由程序生成并写入实验元数据。正式采样不能由帧率或实际运行时间推进。

由此得到：

```text
2 个地形 × 3 条轨迹 × 3 个预算 = 18 个场景单元
18 个场景单元 × 64 个采样点 = 1152 个工作量发现状态
```

### 3.4 每个 Pass 的目标状态

先用 DOD 固定串行增量策略完整运行 1152 个状态，只根据工作量特征选择目标状态，不根据哪个策略更快来选择。

每个 pass 在每个场景单元中选择 8 个目标状态：

- 低工作量区 2 个
- 中工作量区 2 个
- 高工作量区 2 个
- 辅助特征覆盖补点或高依赖状态 2 个

每个 pass 使用下面的字段划分工作量：

| Pass | 主要分层字段 | 辅助覆盖字段 |
| --- | --- | --- |
| 合并评分 | `MergeScore.CandidateCount` | 评分/建堆占比 |
| 细分评分 | `SplitScore.CandidateCount` | 评分/建堆占比 |
| 合并拓扑 | `MergeTopology.CandidateCount` | 内部/边界候选比例、非空分块数量 |
| 细分拓扑 | `SplitTopology.CandidateCount` | 内部/边界候选比例、非空分块数量、预算余量 |
| 网格提交 | `MeshEmit.DirtyItemCount / ActiveTriangleCount` | 预计脏区间数量和碎片度 |
| CPU 上传 | 数据包更新字节数/完整缓冲区字节数 | 更新区间数量和缓冲区容量 |

低、中、高区按主要分层字段排序后分成三等份，再使用固定种子 `20260830` 的稳定散列各取两个。最后两个状态在归一化辅助特征空间中采用最远点补齐。选择器不得读取策略耗时、获胜方式、强制闭合的执行后数量或尚未测得的性能交叉位置。百分位、散列输入、特征归一化和并列处理的完整规则见[正式实验准备与执行计划](24-formal-experiment-preparation-plan.md)。若某个场景没有足够的唯一状态，则记录实际数量和覆盖不足，不复制同一状态凑数。

第一轮配对完成后才能估计性能交叉。若交叉区间附近的独立状态不足，可按[正式实验准备与执行计划](24-formal-experiment-preparation-plan.md)增加一次有上限的边界确认，不能回头改写核心目标清单。

不同 pass 可以选择不同的采样编号，不能为了减少状态数量而强制六个 pass 共用同一组帧。

```text
每个 pass：18 个场景单元 × 8 个目标状态 = 144 个冻结输入
六个 pass：最多 864 个 pass 专用冻结输入
```

冻结输入不长期保存完整节点池。实验程序根据场景、采样编号和输入哈希确定性重建目标状态，每次只在内存中保留当前状态及策略副本。

### 3.5 重复次数和执行数量

每个目标状态对每个合法策略先预热 5 次，再记录 30 次。两策略 pass 交替使用 AB/BA 顺序；网格提交的三个策略循环使用六种排列，避免固定顺序偏差。

| Pass | 目标状态 | 策略数 | 每策略记录次数 | 实测执行数量 |
| --- | ---: | ---: | ---: | ---: |
| 合并评分 | 144 | 2 | 30 | 8640 |
| 细分评分 | 144 | 2 | 30 | 8640 |
| 合并拓扑 | 144 | 2 | 30 | 8640 |
| 细分拓扑 | 144 | 2 | 30 | 8640 |
| 网格提交 | 144 | 3 | 30 | 12960 |
| CPU 上传 | 144 | 2 | 30 | 8640 |
| **合计** | **最多 864 个专用输入** |  |  | **56160** |

预热共执行 9360 次，不写入正式样本。报告必须把“独立冻结输入数量”和“同一输入重复次数”分开，不能把 56160 次执行都描述为独立工作负载。

### 3.6 端到端固定策略确认

完成独立 pass 测量后，在相同 18 个场景单元上运行以下五种固定配置：

1. Classic 外部参考
2. DOD 固定串行 + 增量输出
3. DOD 最大安全并行 + 增量输出
4. DOD 固定串行 + 全量输出
5. DOD 最大安全并行 + 全量输出

每种配置在每次轨迹重复前使用该轨迹的前 8 个采样点预热，随后重置拓扑并正式运行完整轨迹。完整轨迹重复 5 次，并轮换配置运行顺序：

```text
18 个场景单元 × 5 种配置 × 5 次轨迹重复 × 64 个采样点
= 28800 条端到端帧记录
```

端到端预热另有 3600 帧，不写入正式样本。“最大安全并行 + 全量输出”中的完整网格写入仍是 `SerialFull`，只有评分和安全拓扑阶段请求并行。

端到端结果用于确认单 pass 现象在完整流水线中是否仍可观察，不用来替代冻结输入的配对测量。

### 3.7 D3D12 上传交叉检查

D3D12 不重复完整主矩阵。交叉检查固定使用各地形的中预算，即 4096 和 80000。每个“地形 × 轨迹”组合选择 4 个上传状态，覆盖低、中、高脏字节比例和高碎片度：

```text
2 个地形 × 3 条轨迹 × 4 个状态 = 24 个上传输入
24 个输入 × 2 种策略 × 30 次记录 = 1440 次 D3D12 实测上传
```

每个策略仍预热 5 次。D3D12 结果用于检查 OpenGL 上观察到的反转是否依赖单一图形接口，不与 OpenGL 样本直接合并计算一个共同中位数。

### 3.8 明确排除的规模

第一轮正式实验不展开以下组合：

- 1/2/4/8 全线程矩阵
- 第二台 CPU 或跨 CPU 架构比较
- 第三个真实地形和更多高度图
- `ParallelFull` 网格提交
- 10 ms、16.6 ms、20 ms 的完整笛卡尔积
- 所有 96 种整帧策略组合在全部 1152 个状态上的穷举
- 在线模型、迟滞参数和最小驻留时间的联合扫描

这些内容只有在核心实验确认存在稳定 crossover 后才选择性扩展。

## 4. 测量和统计判定

### 4.1 完整 Pass 计时

策略时间必须覆盖整个 pass：

- 评分：评分循环、同步和建堆
- 拓扑：候选快照、分块、队列失效、提交、结果整理、索引与队列刷新以及串行收敛
- 网格提交：拓扑编辑重放、槽位维护、顶点和索引写入以及脏区间整理
- CPU 上传：全部图形接口调用和实际传输准备

状态重建和深复制时间单独记录，不计入策略本身，但必须报告实验总开销。在线策略未来若需要候选快照或分块特征，相应规划成本必须重新计入在线决策成本。

### 4.2 配对顺序

两个策略在同一冻结输入上构成一个配对块：

```text
第 1 块 A -> B
第 2 块 B -> A
持续交替直到每个策略取得 30 个样本
```

网格提交有三个策略，使用六种排列组成平衡顺序，并循环五次。不同目标状态的外层顺序使用固定随机种子打乱。任何策略失败后都要恢复同一冻结输入，不能继续消费已经修改的状态。

核心实验不主动清空 CPU 缓存。所有策略通过相同的状态恢复流程开始，并依靠交替顺序抵消恢复过程带来的缓存影响。这更接近真实流水线中前一 pass 刚刚访问过拓扑和队列的情况。冷缓存只作为后续敏感性检查，不与核心样本混合。

### 4.3 Winner、Tie 和 Crossover

每个策略报告 p50、p95 和最大值。主要比较使用配对耗时差，并进行 10000 次 bootstrap 重采样。

两策略在某个目标状态上满足任一条件时记为 tie：

- 配对耗时差的 95% 置信区间包含 0
- 中位耗时差小于 `max(0.01 ms, 较快策略中位时间的 3%)`

否则，中位时间更短的策略是该状态的 winner。网格提交进行三组两两比较，并对置信区间判定使用 Holm 校正。

一个 pass 只有同时满足以下条件，才声称存在稳定 crossover：

1. 至少出现两个方向相反的 winner 区域
2. 每个区域至少包含 8 个独立冻结输入
3. 区域内至少 70% 的输入支持同一个 winner
4. 聚合配对差异的 95% 置信区间不包含 0
5. 相反 winner 至少在两个不同场景单元中复现

仅在相邻两个采样点上偶然换一次 winner，不足以构成稳定 crossover。

区域级置信区间以冻结输入为重采样单位，不能把同一输入上的 30 次重复当成 30 个独立工作负载。单输入内的重复只用于估计计时噪声和该输入的稳定中位数。

### 4.4 时间预算标签

核心实验只使用 16.6 ms 整帧时间预算。某个 pass 是否可行，要用该帧扣除准备、收尾、其他 pass 和渲染固定成本后的剩余时间判断，不能直接用“该 pass 小于 16.6 ms”作为结论。

10 ms 和 20 ms 只在核心 crossover 成立后做敏感性分析，不增加第一轮执行数量。

### 4.5 回退样本

请求并行但实际执行串行时，该次记录用于统计可行区域和回退率，不进入串行与并行的速度配对。只有两个请求都实际执行了各自目标策略，才能形成性能 winner。

需要分别报告：

- 请求数量
- 实际执行数量
- 各回退原因数量
- 能形成有效配对的冻结输入数量
- 有效并行提交数量和串行尾部比例

## 5. 正确性门槛

任何性能样本只有满足下面全部条件才有效：

- 单结果检查通过且失败掩码为 0
- 相同输入哈希
- 规范化拓扑、活动叶和网格结果等价
- 活动三角形不超过预算
- 长期队列成员和队列不变量正确
- T 形裂缝、非法邻接和非法拓扑数量为 0
- 没有资源检查失败

线程数量、节点池大小、评分条目数量和网格更新数量属于实现成本，可以不同，但必须保留在报告中解释时间差异。

## 6. 实验输出

### 6.1 逐次记录

每次策略执行至少输出：

- `scenarioId`、`terrainId`、`trajectoryId`、预算和采样编号
- `passId`、`frozenStateId`、`repeatIndex` 和执行顺序
- 请求策略、实际策略、线程数量和回退原因
- 完整 pass 时间及已有内部子阶段时间
- 该 pass 的工作量字段
- 输入与结果哈希
- 单结果检查和配对结果

### 6.2 每个 Pass 的报告

每个 pass 单独生成：

- 工作量分布和有效配对覆盖率
- 各策略 p50、p95 和最大值
- winner/tie 区域
- crossover 位置和置信区间
- 回退原因分布
- 内部成本构成
- 不支持 crossover 的证据

Merge 与 Split 的评分、拓扑结果都必须分别成图、成表，不能合并为一个评分或拓扑总时间后判断 winner。

## 8. 继续、停止和扩展规则

- 至少三个具体 pass 出现稳定且位置不同的 crossover，才继续研究通用的 pass 级在线选择
- 某个策略在所有有效工作量上稳定被支配，就从该 pass 的最终策略集合移除
- 细分拓扑始终不能形成真实并行提交时，只保留串行实现和负面实验结论
- 简单工作量阈值已经能稳定选择 winner 时，不引入更复杂模型
- 核心矩阵覆盖不足时优先增加目标状态，不先增加 CPU、线程数量或地形
- 核心结果成立后，线程扩展只选择 24 个代表性冻结输入运行 1/2/4/8 线程，不重跑完整矩阵

这些规则保证实验规模能够执行，也允许“某些 pass 没有 crossover”成为正式结论，而不是为了维持研究叙事继续扩张实验。
