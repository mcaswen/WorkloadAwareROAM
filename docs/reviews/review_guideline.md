# Agent 架构审查规范

本规范用于 Agent 对用户指定的 plan 文档和 Codebase 文档进行审查。

目标是基于已有事实评估方案是否合理，而不是重新执行一次代码探索。

## 1. 信息来源与工具限制

* **只审查用户明确指定的 Plan / Codebase 文件。**
* **在已有文件信息足够的情况下，不要调用工具读取源码、搜索项目或重新探索代码库。**
* 这些事实文档存在的目的之一，就是避免重复产生源码扫描、工具调用和上下文开销。
* 只有当某个关键判断无法从指定文件得到答案，并且该信息会实质性影响审查结论时，才允许进一步查看源码。

## 2. 审查原则

以 Codebase 描述的**当前真实实现**为事实基础，以 Plan 描述的**目标设计**为审查对象。
重点检查 Agent 开发中经常出现的上帝类/文件，分层设计不清晰，打补丁式设计，有重复的可以抽象的数据结构/算法但冗余地分布在多个类中等倾向。

鼓励人类可读的架构/设计，比如多文件分布，合理的设计模式应用，合理的数据结构/算法抽象等。

重点判断：

* Plan 是否建立在正确的当前代码事实之上。
* 是否遗漏已有可复用能力。
* 模块、目录、文件和类型的职责划分是否清晰。
* 是否存在职责过度集中或不必要拆分。
* 数据结构、算法、策略、调度、缓存、状态管理、基础设施等职责是否合理分离。
* 依赖方向是否清晰，是否引入反向依赖、循环依赖或不必要耦合。
* 数据 ownership、生命周期和状态变化是否明确。
* 接口是否与职责边界匹配。
* 实施阶段是否能够独立验证，顺序是否合理。
* Plan 是否遗漏迁移、清理、测试、性能、并发或兼容性风险。
* 是否存在实现后容易形成 God File / God Object、重复逻辑或职责泄漏的设计。

## 3. 审查输出

审查结果应按严重程度组织：

### Critical

会导致方案错误、无法实现、违反核心架构约束或产生严重正确性风险的问题。

### Major

不会立即导致失败，但会产生明显职责混乱、耦合、扩展困难、性能风险或较大返工成本的问题。

### Minor

值得改善但不会实质影响整体架构的事项。

每个问题尽量包含：

* 对应 Plan / Codebase Facts 中的具体位置或设计。
* 问题是什么。
* 为什么这是问题。
* 可能产生的实际影响。
* 建议如何修改。

如果没有实质问题，应明确说明方案可以进入实现阶段，不要为了输出更多内容而制造问题。

## 4. 事实与不确定性

* 不得把 Codebase Facts 中没有支持的信息当成事实。
* 不得根据常见工程习惯猜测项目实际行为。
* 如果审查结论依赖缺失信息，应标记为 `UNCERTAIN`。
* 对于不影响当前方案判断的缺失信息，不需要继续调查。
