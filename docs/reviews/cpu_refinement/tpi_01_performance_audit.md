# TPI-01 迁移性能差值核查

> 2026-09-15。范围限核心/线程依赖迁移；原始程序、命令、逐帧输出和比较见 `benchmark-output/cpu-refinement/tpi-01/run-01/`。这是开发快验，不是正式性能统计。

## 现象与复测

Peking/20k、相同冻结八轮、固定 r=m=64，Release/WSL，同一 CPU 亲和性。下表为移动五帧的调用均值，单位 ms；每格来自一个独立进程，五帧不是五次独立重复。

| 路径 | 首次旧 | 首次新 | 相邻复测旧 | 相邻复测新 |
|---|---:|---:|---:|---:|
| B1 | 38.889 | 48.318 | 42.978 | 38.969 |
| C4 | 19.497 | 25.050 | 19.578 | 23.270 |
| DOD4 | 11.097 | 14.753 | 10.487 | 10.482 |

首次三者同时变慢，复测 B1/DOD4 未持续。C4 复测增加 3.692ms，其中视图刷新增加 3.529ms；视图评分从 4.412 到 6.812ms，投影从 11.031 到 12.011ms。不能凭“仅搬文件”忽略这个观察，也不能直接认定线程工具增加了这些计算。

完整八帧的均值/中位数/描述性 P95、各阶段时间保存在 `performance-comparison.json` 和逐轮 `summary.json`；短序列的 P95 是样本最大值，不能解释成稳定尾延迟。复测顺序反转为新→旧，保留首次全部数据。

## 定向分析

1. 26 个核心文件逆变换路径/命名空间后，与基线逐字相同；原池函数体逆变换名称后也相同。没有新增 Q 扫描、候选维护或更改分块。
2. 初次与复测共 48 份逐帧 mesh 在各自版本配对中逐字相同；32 份事务摘要去除时间后相同，B/C 网格也相同。任务、逻辑访问和配额没有因迁移变化。
3. 旧/新反汇编中 `Project`、两个视图分块入口、`PrepareView`、`Execution::Run`、池 `ParallelFor`、安全 `Dispatch` 的函数长度分别一致。这只能排除明显新增实现工作，不能证明缓存、调度或真实时间相同。
4. 仅对 C4 增加一对 `perf stat` 调度诊断，不扩大矩阵。进程 task-clock 为旧 1089.67ms、新 1074.49ms，缺页为 64674/64676；这些包含初始化与文件输出，不能用来代替视图阶段 CPU 工作。当前计数仅 user 域，context-switches/cpu-migrations 的 0 不能证明没有抢占或迁移。
5. 同一诊断对中，旧程序移动均值升至 28.723ms，新为 25.186ms；视图评分为旧 9.561ms、新 7.877ms。差值反向，旧程序也能产生比迁移后更大的评分延迟。这组带 perf 的时间独立列出，不替换正常计时、不选择较快结果作为验收数。

## 结论与处置

**没有发现迁移增加逻辑工作或足以确认持续版本相关退化的证据。** DOD4 的同环境复测接近；C4 在前两对正常采集中偏慢是保留事实，额外诊断显示同一旧程序自身也有明显时序波动，尚不能确定根因。不得将其写成“优化提高性能”或严格性能等价证明。

本阶段按批准的快速核查范围结束，不再追跑计时或修改原算法寻求好看的数值；记录为“核心/调度兼容通过，C4 短测性能归因有限”。后续公共适配阶段沿用已冻结程序和完整时间边界，若有新的受控证据显示持续同向差异，再在其明确来源处处理。当前不为未确认的原因引入池算法、缓存或候选策略修改。
