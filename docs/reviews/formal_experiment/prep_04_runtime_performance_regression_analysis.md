## 4. 已完成的排查

1. **核对实际工作量与结果。** 普通矩阵十二组的原始 CSV，排除时间和 CPU 利用率后，全部非计时字段逐列一致。最初的粗摘要把 `cpuUtilizationPercent` 也纳入“语义”，它会随运行时间变化；差异已定位并单独处理，没有改写原始 CSV。发现前后共 24 次运行的目标清单 SHA-256 只有一个值，目标身份和选择未变化。
2. **核对同期旧程序。** 首轮已逐进程交替运行旧、新二进制。13 个初始触发项未在同期配对中超过原噪声范围，其余项进入三配置复测。原始全矩阵和首轮异常全部保留，未用后一次覆盖前一次。
3. **核对测量路径。** 普通 benchmark 的证据收集位于 `DataOrientedRoamPipeline.cpp::CollectPassEvidence`，本阶段未修改该函数或生产评分算法。新增 `PassMeasurement`、`PassEvidence` 的完整验证只由配对/旧冻结诊断使用，不能据函数名相似就将普通 `passEvidenceMilliseconds` 的变化归因于新验证器。普通矩阵没有启用新的 CPU pilot 配对入口。
4. **区分新能力成本。** 配对复制、检查和重建单列；新旧工程配对的 wallMs 口径不同，未作速度比较。分析最终容量复测为 2.819 秒、255.09 MiB，包含显式合成大表和真实完成模板的来源审计成本，不是普通应用帧时间。
5. **区分后续 Python 审计修正。** 最后来源完整性、环境分组和单次探测成本修正不在普通 benchmark/发现执行路径内，且两轮使用相同应用二进制。它们不能解释本表中的 C++ 帧时间差。

## 5. 原因与尚未确认的部分

已证实：原始粗语义摘要差异来自利用率观测；原旧程序本身存在显著时段漂移；部分恶化只出现一次；OpenGL 部分指标在两轮配对中继续触发原规则。算法有效工作量增加目前没有证据支持。

UNCERTAIN：普通运行中版本相关差值尚未定位到具体指令、分配或调度事件。编译/链接布局、缓存行为与系统调度的影响尚未拆开验证；这些只是后续排查方向，不能作为已证实原因写入结论。当前也不能仅因相关生产函数源码未改就认定没有性能回归。

## 6. 承接决定

建议新增独立性能修复小规划：先保留本次原始基线与两轮证据，明确受影响包络，进行可复现的调用/编译产物和运行环境定位，再提出有证据支持的修复。具体生产文件归属应由定位结果决定，不能先猜一个优化点就改代码。

另一方式是经用户明确允许后修改后续规划承接，并写明阶段、验收责任及可继续范围。无论采用哪种方式，复测仍需对照 PREP-04 退化前原始基线，不能以当前较慢结果替换唯一基线。细分拓扑不等价仍会独立阻断完整 CPU 配对验收。

## 7. 规划前补充调查：环境对照与函数机器码

### 7.1 来源与设计

现有 PREP-04 已按用户要求先提交：代码 `7522db7`，文档 `a738f78`。随后仅运行原保留程序与相同的新程序，两份二进制未改变，生产源码身份前后一致。调查工具与原始结果保存在：

旧/旧五个块差为 `[-0.177950, +0.736475, -0.568700, -0.799725, +0.186325]` ms，与历史版本差值处于同一量级。同一个旧版本在不同处理器分组下也有明显不同耗时。因此整帧恶化不是稳定的新版本特征，处理器选择与时段是必须控制的影响因素。不能将分组差全部解释为缓存容量：频率、调度和可用处理器也随限制改变。

仍有局部疑问：96 MiB 分组下的 `pass_splitScoreHeapifyMs`，五个块差依次为 `+0.002900/+0.001300/+0.002475/+0.001025/+0.002000` ms，均为正。其他条件下方向和波动不相同；不能以整帧改善覆盖该项。

### 7.3 指令与计时边界核对

`DataOrientedRoamQueues.obj` 修改时间早于原性能基线归档。以其 COFF 符号和重定位描述定位函数，在两份 PE `.text` 中分别得到唯一匹配：

| 函数 | 字节数 | 旧 RVA | 新 RVA |
| --- | ---: | ---: | ---: |
| `SiftSplitQueueDown` | 192 | 417248 | 432016 |
| `SplitEntryPrecedes` | 49 | 418272 | 433040 |
| `RefreshPersistentSplitQueuePriorities` | 891 | 414032 | 428800 |

排除明确列出的链接重定位字节后，这些函数主体指令相同。该证据排除“这三个函数被重新编译成不同主体指令”的解释，未比较所有调用目标，也未证明布局、缓存或性能一致。具体归一化摘要及排除区间已保存，不能把它扩写为整个程序机器码相同。

另确认普通 `MakeScenario` 开启 `EnablePassEvidence`；`standard/budget-saturation` 关闭的是拓扑验证。外层帧计时包含证据收集，内部 `CpuUpdateMilliseconds` 在它之前结束。原矩阵尚未覆盖三个诊断开关全关时的生产成本，修复规划已列入独立 CPU 调用对照。

### 7.4 原因判断与下一步

FACT：处理器限制能明显改变相同二进制的耗时；相同程序对照存在与疑问版本差值同量级的波动；本轮整帧和证据收集的版本差为负；96 MiB 条件下仍有较小的建堆正差；三个队列函数主体匹配；原诊断关闭对照缺失。

INFERENCE：后续应优先修正测量环境控制与覆盖缺口，再针对建堆调用链和链接布局定位。UNCERTAIN：历史每个异常的调度/频率贡献、剩余微小差值的代码或布局根因。未实施绑核优化、堆算法修改或强制对齐，未宣告性能问题关闭。
